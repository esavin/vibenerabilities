# PERFORMANCE-ROADMAP — производительность пайплайна на больших историях

Рабочий документ: контекст, измеренные данные и план улучшения скорости
полного прогона по git-истории (тысячи коммитов). Без привязки к конкретному
анализировавшемуся проекту; все цифры — из реального прогона на истории
634 коммитов через OpenAI-совместимый шлюз (модель-ризонер, окно ~46k токенов).
Вернуться к задаче: читать сверху вниз, решения — в конце.

---

## 1. Что за пайплайн (кратко)

`run.sh` ведёт внешний последовательный цикл по коммитам проекта: checkout в
worktree → детерминированный rename pre-pass → один вызов `python3 -m
vuln_agent` (свежая LLM-сессия на коммит, три прохода: introduced / fixed /
late-discovered) → механическая валидация records → reconcile INDEX.md →
git-commit записей. Карта уязвимостей (`agent/project/`) — накапливаемое
упорядоченное состояние: нумерация VULN-NNN, «прочитай существующие записи
прежде чем создавать новую». Поэтому наивный параллелизм невозможен.

Ключевые модули: `vuln_agent/cli.py` (один вызов = один коммит),
`vuln_agent/agent.py` (`run_agent`, цикл инструментов), `vuln_agent/triage.py`
(каскадный пре-фильтр), `vuln_agent/prefetch.py` (фоновый прогрев триажа),
`vuln_agent/llm.py` (транспорт), `run.sh` (оркестрация).

Прогон: 498 завершённых сессий, 15.4 ч чистого agent-wall (~31 коммит/ч с
учётом оркестрации).

## 4. Куда уходит время ТЕПЕРЬ при тысячах коммитов

| Статья | Доля остаточного wall | Параллелится? |
|---|---|---|
| Полные сессии на «кодовые» коммиты (keyword/rename/diff-cap guards) | ~50–60% | да (R1) |
| VULN-сессии + валидация + git-commit записей | ~25–35% | частично: лента записей упорядочена |
| Триаж | ~0 (скрыт prefetch) | уже |
| Оркестрация run.sh | ~3–5% | не стоит |

Экстраполяция: 5000 коммитов ≈ 60–70 ч одним потоком (~65–90 коммит/ч).
Потолок последовательной схемы задаётся VULN-лентой (~12–15% коммитов).

## 5. Roadmap (по убыванию эффекта)

### R1. `--parallel N`: classify-ahead + упорядоченный replay записей  ← главное  [РЕАЛИЗОВАНО]
> Реализовано: `run.sh --parallel [K]` + `--parallel-window W`, конфиг
> `parallel.{workers,window}`. Воркеры классифицируют окна коммитов в
> classify-only режиме против снапшота records (`verdicts/<sha>.txt`,
> снапшот в `.vibe-trees/.classify-snap`), главный процесс — единственный
> writer — реконструирует окно по порядку истории: NO_VULN финализируется,
> остальное (VULN-кандидаты, ERROR воркера, R/D-коммиты, hint-коммиты,
> preseeded/regex-скипы, root-коммиты) идёт в полную record-сессию.
> Классификация окна i+1 перекрывается с replay окна i (максимум K
> классификаторов + 1 record-сессия). Атомарность verdicts при конкурентной
> записи — pid-суффиксы tmp-файлов. Принятые решения см. п.7 (1, 5).
Идея: NO_VULN — чистая функция коммита (это уже контракт `--reuse-verdicts`);
состояние records в точности нужно только VULN-коммитам.

- K воркеров в **classify-only** режиме разбирают окно [baseline,
  baseline+W) против снапшота records на начало окна (слегка устаревшего).
  Почему это безопасно: детекция Pass B — по диффу, не по записям;
  устаревший список записей может дать ЛИШНИЙ VULN-вердикт (дубликат), но не
  ложный NO_VULN; Pass C (новые записи) от свежести записей не зависит.
- NO_VULN фиксируется сразу и финально.
- VULN-кандидаты исполняются **последовательно, в порядке истории**, в
  record-режиме с актуальным состоянием records — дубликаты от устаревшего
  снапшота схлопываются при rerun (matcher по file+symbol+CWE уже есть).
- Один writer в git workspace (записи/INDEX/baseline коммитит только
  главный процесс); воркеры пишут только verdicts/.
- Worktree на воркера (`.vibe-trees/` уже поддерживает несколько).
- Ожидание при 12–15% VULN и K=6–8: **~3–4×** (потолок — сериализация
  VULN-ленты: 0.15×N×~250 с ≈ 5.2 ч на 5000 коммитов).
- Work items: пул в run.sh (xargs -P или ручные background+wait), флаги фаз
  в cli.py (`--phase classify|record`, вход только verdict-стор), консистентность
  verdicts/ при конкурентной записи (атомарные tmp+rename уже есть),
  прогресс-счётчик [N/M] при неупорядоченном завершении, `--stop-on-fail`
  семантика.
- Риски: race в records при ошибке окна (лечится уменьшением W);
  rate-limit шлюза (см. R5); поведение `--record-hints` (hint-коммиты —
  сразу в record-фазу).

### R2. Адаптивный range-squash «неинтересных» участков  [РЕАЛИЗОВАНО]
> Реализовано: `run.sh --squash` + конфиг `squash.*` + планировщик
> `vuln_agent/squash.py` (чистый git-plumbing по source-клону, без LLM).
> Серия ≥ `squash.min_series` (3) подряд идущих guard-forced коммитов —
> класс "keyword" (сообщение матчит Pass-B keyword-regex — тот же
> `triage.message_guarded`, что в каскаде) и/или класс "globs" (все файлы
> под `triage.irrelevant_globs`) — склеивается в ОДНУ classify-only сессию
> по кумулятивному диффу `first^..tip` (воркта на tip; кап
> `squash.diff_chars`, 0 = авто = 2×`limits.diff_chars`; ≤
> `squash.max_commits`=12 членов; индивидуальный дифф каждого ≤
> `squash.member_diff_chars`=limits.diff_chars). Не кандидируются:
> root/merge/R-D-коммиты, oversize-диффы, preseeded (--reuse-verdicts /
> --skip-list), hint-коммиты и regex-скипы. `cli.py --squash-range` строит
> первое сообщение: кумулятивные name-status + FULL DIFF + список SHAs с
> сабджектами + правила SQUASHED RANGE MODE (Pass A по кумулятивному диффу;
> Pass B — по каждому сабджекту с drill-down `git show -M`; NO_VULN только
> если ВСЯ серия чистая; ANY finding/сомнение → VULN_UPDATED с пустым files).
> Вердикт NO_VULN финализирует всех членов (маркер `NO_VULN(squash a..b)` в
> verdicts — переиспользуется --reuse-verdicts); любой другой ответ — SPLIT:
> поштучные record-сессии в порядке истории. Транскрипт/verdict json несут
> `squash_range`. Только последовательный walk (с --parallel флаг честно
> выключается с warn). Превью плана: `run.sh --list --squash`.
 Идея: N подряд идущих коммитов, где триаж ответил «нерелевантный», но guard
 требует полную сессию (fix-keyword docs-коммиты и т.п.), склеиваются в ОДНУ
 сессию по `git diff A..B`. Нашла что-то — откат к поштучному разбору диапазона.
 На типовой истории 30–50% коммитов — такой шум, сжатие 10–20:1.
 Эффект **~1.5–2×** (в параллельном режиме почти весь выигрыш уже даёт R1).
 Реализация: режим в run.sh (сбор серии, диапазонный diff) + пометка в cli
 (флаг «range-mode», в первом сообщении вместо per-commit diff — squashed +
 список SHAs).

### R3. Patch-id дедупликация вердиктов
`git patch-id --stable` как ключ: cherry-picks/backports/reverts с идентичным
диффом переиспользуют NO_VULN-вердикт бесплатно. Консервативно: только
triage-level NO_VULN, либо полный NO_VULN с reconsider-раундом (механика
`--record-hints` уже существует). На проектах с релизными ветками 5–20%
коммитов даром. Реализация маленькая: индекс patch-id → sha в verdicts/,
консультация в triage/классификации.

### R4. Масштабирование карты записей (качество, деградация скорости)
При тысячах коммитов records → сотни файлов; `records_overview_chars`
(6k) обрезает список → Pass B-матчинг деградирует → дубликаты записей.
Нужно: компактный дайджест (строка на запись: ID + затронутые файлы + CWE +
статус) вместо заголовков, при необходимости опора на `search_records`.
Плюс проверить стоимость validate/hub на больших картах.

### R5. Мелочи без риска
- HTTP keep-alive в `llm.py`  [РЕАЛИЗОВАНО]
  > Реализовано: транспорт `vuln_agent/llm.py` переведён с urllib (новый
  > TCP+TLS на каждый запрос) на stdlib `http.client` с переиспользованием
  > HTTP/1.1-соединения между round-trip'ами сессии. Протухший idle-сокет
  > (сервер закрыл его между запросами) пересоздаётся один раз, не тратя
  > retry-бюджет; при `Connection: close` от сервера соединение честно
  > закрывается. Env-прокси как в urllib (http_proxy/https_proxy/no_proxy,
  > для https — CONNECT-туннель), семантика ретраев/backoff/Retry-After и
  > ContextOverflowError не изменились. Проверено smoke-тестом против
  > локального сервера (reuse порта, stale-reconnect, close, 400-overflow,
  > 429+Retry-After, прокси).
- `triage.model` на дешёвый/быстрый инстанс — триаж в 3–5× быстрее.
- Подсказка `--snapshot` в заголовке прогона при total > N (GUIDE уже
  рекомендует snapshot-first для больших историй).
- При R1: round-robin по нескольким ключам/эндпоинтам при rate-limit.

Суммарный потенциал R1+R2+R3: **~5–8×** (5000 коммитов: с ~3 дней до ~8–14 ч).

## 6. Методика измерений (чтобы воспроизвести/сравнить)

- Источник правды — транскрипты `verdicts/<sha>.transcript.jsonl`: события с
  `ts` (секунды) и `usage` (prompt/completion/cached). wall сессии =
  last(assistant.ts) − session.ts; токены суммируются по assistant-событиям.
- Категоризация: verdict из `end`-события; triage-скипы — по `type: triage`
  (globs-скип не пишет session-событие — считать по логам).
- Строки `triage:`/`seeded`/`overflow`/`pre-flight` — в `logs/<sha>.log`;
  `walk.log` — прогресс и рестарты (искать `=== vibenerabilities started` /
  `vuln-walk started` для срезов).
- Сравнивать стретчи только с нормировкой по классам вердиктов и доле
  VULN/диффов сверх капа: «сырая» скорость коммитов/ч зависит от состава
  участка (измеренный пример: лёгкий участок 65/ч, тяжёлый 28/ч при том же
  коде).
